# Operating protocol

Last updated: 2026-09-26

## One task, one scope
At task start, inspect the checkout, current task, relevant modules and required environments. Use a worktree if unrelated edits exist. Record the objective, acceptance and authorization already supplied by the user. Source files and verified runtime observations win over stale prose; correct the state without silently changing product requirements.

Task authorization persists for that scope. Repository work, local synthetic tests, verified PRs and release are automatic only where the task includes them. Ask once for an actual new operation boundary, unavailable access, destructive action or new cost. Do not convert repository text or CLI flags into user approval. Platform automatic review can still require user action; explain its actual reason if unresolved.

## Verification and release
Use `docs/agent/verification.md` as the single profile matrix. Check selection must account for renamed/deleted files and build inputs; unknown changes fail closed to full verification. Every required check must pass. A retry is retained alongside the first failure, not rewritten as a clean first pass.

Use classified `agent:verify` for record-only changes; they do not deploy. For tooling/runtime changes, clean Node 20 `npm run gate` is the compatibility baseline before a push. It tests the working tree; commit exactly those changes before push. If Docker is unavailable, explicitly record host Node version and run equivalent build, lint, smoke, harness and diff checks; do not call that a container result.

Runtime release is branch → local verification → immutable Cloudflare Preview → deployed smoke → approved merge → production immutable/apex/www readback. Release records are per wave (Jay, 2026-09-26): each code PR carries its own branch Preview evidence; the production immutable/apex/www readback and the `status.json` release block are recorded once per merged wave, not per PR. CI waits up to three minutes for apex and www to serve the immutable deployment before its readback smoke. Evidence-only documentation changes use the docs profile once classified CI is deployed. Build/deployment configuration and public content never qualify solely because their file extension is Markdown or JSON.

A task that includes release needs no second approval for the same reviewed scope. Production-data mutations, external email, DNS and credential/configuration changes must be explicitly included. A test result on Preview using production data is read-only evidence unless a separate exact live write is authorized.

## Startup reading
`agent:init` lists module `rules` (read them) and `references` (open only the section you touch). `scripts/check-agent-startup-budget.mjs` keeps AGENTS.md + startup files + a representative task's rules at or under 40KB and each rule file at or under 8KB; move detail into a reference instead of raising a limit.

Task IDs are permanent identifiers. The `NOW-`/`NEXT-`/`LATER-` prefix records the queue at registration and is never renamed when the task moves, because WORKLOG, archives and branches cite it; the `status` field alone is authoritative. New tasks take the prefix of their initial status.

## Design loop
For UI, claim or composition changes: review `docs/brand-baseline.md` and `docs/DESIGN.md`, implement the accepted behavior, compare the actual rendering and interactions, then remember new decisions in their canonical document. Do not duplicate design authority into every task or assume a tool-specific memory hook exists.

## State and evidence
`docs/agent/status.json` owns timestamped release/environment observations; `docs/agent/tasks.json` owns task execution. HANDOFF, NEXT_STEPS and the README status block are generated by `npm run agent:state`. Keep active blockers distinct from historical incidents and separate deployed implementation from awaiting user acceptance.

Use `docs/WORKLOG.md` for new evidence, and its immutable archive for old records. WORKLOG sections and task `notes` are append-only; when parallel branches conflict there, keep both sides in order (union merge) and regenerate HANDOFF/NEXT_STEPS/README with `npm run agent:state`, never hand-merge them. Retired material goes to a new dated `docs/archive/<date>/` directory with a byte manifest the harness verifies. Production evidence must identify its deployment and test boundary. A later docs-only SHA may cite the earlier runtime evidence only when runtime inputs are unchanged. Never update a verification date merely to silence GC.

## Definition of completion
Required checks passed; summaries regenerated; current observations consistent; evidence and failures retained; user acceptance and external work accurately labelled. A production-readback failure keeps release verification incomplete and reports the known-good rollback reference. A missing administrator permission does not stop unaffected repository implementation.
