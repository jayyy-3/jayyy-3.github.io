## Current Focus
The launch direction is now Cloudflare Pages + Supabase + an Urblo-owned admin CMS:
- Public website hosting should move to Cloudflare Pages.
- Contact and Sample Request source now uses Supabase-backed Pages Function submissions instead of mailto/local-only main submit behavior; production persistence still depends on server-side environment verification.
- Projects, Stone Library, Products, Articles, media records, and lead records should become customer-maintainable through `/admin`.
- The current content runtime remains static/file-backed until content migration tasks are completed.
- The long-form plan and cost baseline live in `docs/SUPABASE_CLOUDFLARE_LAUNCH_PLAN.md`.
- Supabase project access is available through the connector for project `Urblo` (`npkidywzwddbnfrnxlmo`, `ap-southeast-2`); foundation and baseline seed migrations are applied.
- Forms backend source is implemented for `/api/enquiries` and `/api/sample-requests`, including server-side audit-event attempts after successful lead inserts, with live Supabase insert verification pending server-side `SUPABASE_SERVICE_ROLE_KEY` configuration.
- Live form persistence verification now has a credential-gated runner: `npm run agent:forms-live`. It verifies valid enquiry/sample-request rows, sample item rows, server-side audit rows, and invalid-payload no-write behavior once a service-role key is configured. The runner intentionally fails without credentials and retains tagged test rows until cleanup is approved.
- `/admin` auth shell source is implemented and config-gated. Without a browser-safe Supabase key, admin routes show a configuration-required state and do not render dashboard content. Live login/profile verification still requires `VITE_SUPABASE_ANON_KEY` or `VITE_SUPABASE_PUBLISHABLE_KEY` plus Jay's first admin email/profile.
- Admin credential/profile readiness now has a read-only runner: `npm run agent:admin-live-readiness -- --admin-email <first-admin-email>`. It verifies browser-safe key presence, service-role verification access, the named active admin profile, and baseline seed rows without mutating Supabase.
- Cloudflare Pages repo-side readiness now has a no-secret runner: `npm run agent:cloudflare-readiness`. It verifies build settings, clean-route fallback, `/api/*` Function routing scope, launch headers, API handler files, env placeholders, and the deployment runbook before account-level Pages setup.
- Cloudflare Pages deployed-preview smoke now has a no-secret runner: `npm run agent:cloudflare-preview-smoke -- --base-url https://<preview>.pages.dev`. It verifies direct-refresh public/admin route shells, deployed assets, Cloudflare-applied legacy redirects, and no-write API safe-failure behavior after a Pages preview URL exists. Local Vite preview URLs validate route/asset checks and skip Cloudflare-only redirect/Function checks.
- `/admin/settings` source is implemented for the default `site_settings` row plus admin profile management for existing Supabase Auth users. Supabase migrations `admin_settings_role_hardening`, `admin_profile_owner_hardening`, and `security_definer_function_grants` are applied so settings writes require owner/admin, owner-role profile changes stay owner-protected, and anonymous direct execution of admin SECURITY DEFINER helpers is revoked.
- Supabase media Storage source is implemented. Migrations `media_storage_foundation` and `media_storage_listing_hardening` are applied, creating `urblo-public-media` and `urblo-admin-media` buckets with admin/editor object-write policies and no broad public object-listing policy.
- `/admin/media` source is implemented as a protected media library screen for upload-backed draft records, external records, metadata editing, audit-gated visible manifest export, and publish/archive validation. Live upload/save/export verification still requires browser-safe Supabase key configuration plus an active admin/editor profile.
- `/admin/stone-library` source is implemented as the first content CRUD screen. It can load Stone Library groups, variants, finish definitions, and finish capabilities from Supabase; active editor/admin/owner roles can save group and variant records, publish/archive them, and update per-finish capability rows once browser-safe Supabase config and an active profile exist.
- `/admin/projects` source is implemented as the next content CRUD screen. It can load and save project records, facts, material schedule rows, material maps, and hotspots from Supabase; active editor/admin/owner roles can draft, publish, and archive project/map/hotspot records once browser-safe Supabase config and an active profile exist.
- `/admin/products` source is implemented as the next content CRUD screen. It can load and save product families, product models, material defaults, and product specs from Supabase; active editor/admin/owner roles can draft, publish, and archive product/model records once browser-safe Supabase config and an active profile exist.
- `/admin/articles` source is implemented as the next content CRUD screen. It can load and save article metadata and structured block rows from Supabase; active editor/admin/owner roles can draft, publish, and archive article/block records once browser-safe Supabase config and an active profile exist.
- `/admin/leads` source is implemented as the first lead workflow screen. It can load enquiries, sample requests, sample request items, active admin profiles, Stone Library labels, and finish labels from Supabase; active owner/admin roles can update lead status, assignment, internal notes, and export the currently loaded queue to CSV once browser-safe Supabase config and an active profile exist. CSV export is blocked unless an `admin_audit_events` row is recorded first.
- `/admin/audit` source is implemented as the first audit visibility screen. It can load audit events and active admin profile labels from Supabase; active owner/admin roles can inspect action/entity/metadata history once browser-safe Supabase config and an active profile exist.
- Admin Settings, Media, Stone Library, Projects, Products, Articles, and Leads save flows now call `src/lib/adminAudit.ts` after successful primary mutations. Audit insert failure is surfaced in the success notice and does not roll back the primary save. Live audit row creation verification still requires browser-safe Supabase key configuration and an active admin/editor or owner/admin profile.
- Admin source coverage now has a no-secret runner: `npm run agent:admin-crud-coverage`. It verifies `/admin` route/module registration, protected shell coverage, expected Supabase table references, role-gated controls, publish/archive paths, audit writer actions, and Media/Leads export audit gates without mutating Supabase.
- Admin live write verification now has a credential-gated runner: `npm run agent:admin-crud-live`. Default mode is plan-only and performs no writes. With `--allow-writes`, it requires a browser-safe Supabase key plus a real owner/admin Supabase Auth session and creates tagged draft/archived QA rows plus audit events through browser-key RLS. It does not physically delete data; optional `--include-storage` verifies private Storage upload policy.
- Static-to-Supabase content import preparation has a no-write dry-run command: `npm run agent:content-import`. It maps current static Stone Library, Products, Projects, Articles, and media candidates into Supabase-shaped draft payloads and fails on missing assets or unknown stone/finish references before any database import is attempted. It can also write a local ignored review artifact with `npm run agent:content-import -- --out .tmp/content-import-preview.json`, a paired JSON + Markdown apply/rollback plan with `npm run agent:content-import:plan`, or a paired JSON + Markdown + read-only target preflight SQL bundle with `npm run agent:content-import:preflight-sql`.
- Public Supabase cutover readiness now has a no-write source verifier: `npm run agent:public-supabase-readiness`. It verifies static-to-Supabase import rows remain `draft`, the import has zero warnings/blockers, public RLS policy source is published-only, anonymous grants are read-only, public runtime code remains static/file-backed, and Cloudflare routes only invoke Pages Functions under `/api/*`.
